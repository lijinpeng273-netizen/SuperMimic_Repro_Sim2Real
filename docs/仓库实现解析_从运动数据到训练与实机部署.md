## 1. 整体实现思路

**这套方案训练的是一个“参考动作驱动、传感器反馈闭环”的控制策略。参考动作规定要做什么，策略根据机器人当前状态决定电机目标。**

训练时，它在物理仿真中收集机器人状态转移，拟合一个可微的世界模型，再沿世界模型展开的轨迹反向传播，优化控制策略。部署时只运行训练好的策略，世界模型和价值网络留在训练端。

~~~mermaid
flowchart TD
    A["人体视频或已重定向的 G1 动作 CSV"] --> B["50 Hz 动作 NPZ：重采样、速度、正运动学"]
    B --> C["动作可行性修改、过渡拼接、动作库"]
    C --> D["MuJoCo Warp 并行仿真采样"]
    D --> E["Replay Buffer：状态与动作转移"]
    E --> F["拟合可微世界模型"]
    E --> G["采样策略训练的初始状态"]
    F --> H["世界模型内展开 32 步并优化策略"]
    G --> H
    H --> D
    H --> I["导出 ONNX 策略、控制配置和参考目标表"]
    I --> J["共用部署代码的 Sim2Sim 验证"]
    J --> K["G1 实机：50 Hz 策略与 500 Hz 指令发布"]
    K --> L["实机日志分析"]
    L --> C
    L --> M["修正仿真模型、观测模型、训练起点和奖励"]
    M --> D
~~~

这里有三个容易混淆的概念：

| 名称 | 在本仓库里的含义 | 是否在真机运行 |
|---|---|---|
| 参考动作 | 一条预先准备的机器人运动轨迹，提供关节、根部姿态和速度等目标 | 以预计算目标表的形式读取 |
| 世界模型 | 根据状态、动作和仿真环境参数预测下一步状态的神经网络，另有终止概率预测 | 否 |
| 控制策略 | 根据观测历史和参考动作窗口输出 29 维动作 | 是，导出为 ONNX |

**算法分类上，更准确的理解是基于可微世界模型的策略优化，具有基于模型强化学习的结构。** 它仍然使用奖励、价值网络和仿真采样；区别在于策略梯度通过预测动力学反向传播，而非使用 PPO 的概率比率目标。README 中“不用靠强化学习反复试错”的通俗说法，不宜理解成完全没有强化学习要素。

## 3. 导出运动数据以后，怎样变成训练输入

### 3.1 首先需要的是 G1 参考轨迹

视频流程是：

~~~text
视频统一到 30 fps
    → GVHMR：估计世界坐标系下的人体 SMPL-X 运动
    → GMR：将人体动作重定向到 G1 的 29 个关节
    → 关节范围处理、脚底落地处理、首帧 xy 对齐
    → G1 CSV
~~~

仓库也能直接接收其他重定向工具产生的兼容 CSV。若已经获得 G1 参考轨迹，可以从后面的 CSV 转换阶段开始。

标准无表头 CSV 每帧 36 列：

| 列 | 内容 | 约定 |
|---|---|---|
| 0–2 | 根部位置 | 米 |
| 3–6 | 根部四元数 | xyzw |
| 7–35 | 29 个关节角度 | 弧度，固定 G1 关节顺序 |

格式检查和关节顺序非常重要：同样都是 29 个数字，若顺序不同，训练和电机发送的含义就会不同。

代码位置：[docs/VIDEO_TO_MOTION.md](VIDEO_TO_MOTION.md) 第 5–39 行；[tools/video2motion/gvhmr_to_supermimic.py](../tools/video2motion/gvhmr_to_supermimic.py)；[src/supermimic/data/motion_convert.py](../src/supermimic/data/motion_convert.py) 第 7–22 行和第 35–81 行。后者的 load_csv（第 160 行）还支持 BONES-SEED 的单位和欧拉角格式转换。

### 3.2 CSV 转 50 Hz NPZ，会补齐训练所需的运动学信息

转换过程包含：

1. 检查输入列数和关节顺序。
2. 将四元数从 xyzw 转换到内部使用的 wxyz。
3. 把位置、关节角重采样到 50 Hz；旋转使用四元数球面插值。
4. 从重采样后的信号计算关节速度和根部线速度，用 SO(3) 差分计算角速度。
5. 通过 G1 模型的正运动学，计算身体各 link 的位置、姿态和速度。

因此，输出 NPZ 除了关节轨迹，还包括身体跟踪奖励需要的各部位参考状态。

| 训练 NPZ 字段 | 典型形状 | 用途 |
|---|---|---|
| joint_pos | T × 29 | 参考关节角 |
| joint_vel | T × 29 | 参考关节速度 |
| body_pos_w | T × 30 × 3 | 身体位置目标 |
| body_quat_w | T × 30 × 4 | 身体姿态目标，wxyz |
| body_lin_vel_w | T × 30 × 3 | 身体线速度目标 |
| body_ang_vel_w | T × 30 × 3 | 身体角速度目标 |
| fps、joint_names、body_names | 元信息 | 时间和索引对齐 |

其中 T 是帧数。关节和身体数据由同一条重采样后的运动计算，避免“关节轨迹改了，但速度或身体目标没有同步更新”。

代码位置：

- [scripts/data/csv_to_npz_batch.py](../scripts/data/csv_to_npz_batch.py)，第 47–108 行，main：批量转换、默认输出 50 Hz、写 manifest。
- [src/supermimic/data/motion_convert.py](../src/supermimic/data/motion_convert.py)，resample_motion（第 186 行）、forward_kinematics（第 265 行）、convert_csv_to_npz（第 307 行）。

### 3.3 动作能重定向，不等于真机能够稳定执行

重定向主要满足姿态和运动学关系。高速转体、落地冲击、执行器响应和 IMU 饱和，可能使看起来合理的参考轨迹难以在真机执行。因此仓库在训练前后还会修改参考动作本身：

| 处理 | 解决的问题 | 代码或文档 |
|---|---|---|
| 动作筛选 | 持续悬空、地面穿透、需要额外支撑等不适合当前任务的动作 | [scripts/data/filter_bones_seed.py](../scripts/data/filter_bones_seed.py)，规则见 [METHOD.md](METHOD.md) 第 131–148 行 |
| 关节速度平滑/限制 | 参考本身存在速度尖峰，逼迫策略产生过快动作 | [scripts/deploy/cap_joint_velocity.py](../scripts/deploy/cap_joint_velocity.py) |
| 膝关节可行性修改 | 膝关节过快、接近伸直后再次快速弯曲 | [scripts/deploy/knee_feasibility.py](../scripts/deploy/knee_feasibility.py) |
| 转体与落地修改 | 偏航过快、落脚姿态和落脚点不合适 | [scripts/deploy/spin_feasibility.py](../scripts/deploy/spin_feasibility.py) |
| 开头/结尾站姿与动作拼接 | 接管时突变，或者动作结束后难以原地站稳 | [scripts/deploy/make_combo_clip.py](../scripts/deploy/make_combo_clip.py) |

拼接使用平滑过渡，并重算整段速度及刚体状态。最后一帧也需要适合作为站立参考，才能支持部署端的 STANDBY_POST。

代码位置：[docs/CUSTOM_MOTIONS.md](CUSTOM_MOTIONS.md) 第 54–97 行。转体舞蹈的实际修改过程见 [docs/REAL_ROBOT_LEAN35KFS.md](REAL_ROBOT_LEAN35KFS.md) 第 50–84 行；其中早期的骨盆倾斜修正使用过未纳入仓库的一次性脚本，不能认为整个动作制作过程都已完整开源。

### 3.4 少量动作直接读 NPZ，大量动作打包成紧凑库

训练可以直接使用一个 NPZ 目录，也可以使用 build_library.py 生成的单个 .pt 动作库。

紧凑库只保存每帧 71 维参考状态：

~~~text
根部位置 3 + 根部四元数 4 + 关节角 29
+ 根部线速度 3 + 根部角速度 3 + 关节速度 29
= 71
~~~

打包默认使用 fp16，即参考状态主体约 142 字节/帧；身体 link 状态与目标特征在训练时按需计算。这让十万级动作库不必常驻保存所有 link 的完整状态。

**这里要区分两个数据容器：**

| 容器 | 数据来自哪里 | 训练中用来做什么 |
|---|---|---|
| MotionLibrary | 人体动作重定向后的参考运动 | 给出目标、重置姿态和动作时间索引 |
| ReplayBuffer | 当前策略在物理仿真中的实际交互 | 拟合机器人动力学，提供想象轨迹的起始状态 |

世界模型的状态转移监督来自 ReplayBuffer。参考运动并没有提供“施加某个控制动作后，真实物理系统怎样变化”的完整监督。

代码位置：[scripts/data/build_library.py](../scripts/data/build_library.py) 第 18–38 行；[src/supermimic/envs/mdp/motion_library.py](../src/supermimic/envs/mdp/motion_library.py) 第 1–24 行和第 79–155 行；[src/supermimic/data/replay_buffer.py](../src/supermimic/data/replay_buffer.py) 第 1–59 行。

## 4. 训练具体怎样进行

### 4.1 训练入口和仿真平台

入口关系如下：

~~~text
sm-train
    → supermimic.scripts.train.main()
    → tyro 解析 TrainConfig
    → Trainer(cfg)
    → Trainer.run()
~~~

训练平台是 mjlab / MuJoCo Warp。默认每张卡创建 4096 个环境，物理步长 0.005 秒，每 4 个物理步执行一次策略，策略周期为 0.02 秒，即 50 Hz。

默认训练 episode 最长 10 秒，也可以在动作结束或跌倒条件触发时结束。长舞蹈通过不同起始帧的局部训练覆盖；评测和部署可以从头连续跑完整段，因此“训练 episode 10 秒”不意味着“只能执行 10 秒动作”。

### 4.2 策略看到哪些信息

策略输入由“机器人观测历史”和“参考动作窗口”组成。

每一帧机器人观测为 93 维：

| 观测项 | 维数 | 含义 |
|---|---|---|
| q − q0 | 29 | 当前关节角相对默认姿态的偏差 |
| dq | 29 | 当前关节速度 |
| pelvis gyro | 3 | 骨盆 IMU 角速度 |
| projected gravity | 3 | 重力方向在机体坐标系中的投影 |
| previous action | 29 | 上一步策略的原始输出 |
| 合计 | 93 | 连续 10 帧形成 930 维历史输入 |

每一帧参考目标为 68 维：

| 目标项 | 维数 |
|---|---|
| 参考关节角 − q0 | 29 |
| 参考关节速度 | 29 |
| 参考骨盆重力投影 | 3 |
| 参考骨盆角速度，机体坐标系 | 3 |
| 参考骨盆线速度，参考航向坐标系 | 3 |
| 参考骨盆高度 | 1 |
| 合计 | 68 |

连续 10 个目标帧形成 680 维输入，给策略约 0.2 秒的前瞻信息。

**实际机器人输入不包含全局位置和基座线速度，因此部署无需额外提供这两项状态估计。** 目标中的“参考速度”和“参考高度”来自离线动作文件，不是机器人在线测得的真实速度和高度。姿态观测仍依赖机载 IMU 的姿态估计。

可选的 --env.anchor-obs 会添加参考与机器人之间的相对锚点位姿。这能改善部分仿真结果，但当前真机接口没有相应定位输入，所以导出函数会拒绝这种模型。

- [src/supermimic/world_model/heads.py](../src/supermimic/world_model/heads.py)，第 30 行 analytic_observation、第 57 行 flatten_history_term_major。

### 4.3 策略网络如何把目标变成动作

~~~text
680 维目标窗口
    → MotionEncoder：2048 → 1024 → 512 → 256 → 32
    → tanh，得到 32 维运动隐变量 z

z 与 930 维观测历史拼接
    → Decoder：2048 → 1024 → 512 → 256 → 29
    → 29 维动作 a
~~~

输出动作经缩放得到关节目标：

$$
q_{\mathrm{target}} = q_0 + \mathrm{scale}\odot a
$$

这里 q0 是默认关节姿态，scale 是每个关节对应的动作缩放。动作表达的是相对默认姿态的控制量；参考轨迹通过网络输入影响输出。

底层使用 PD 关系：

$$
\tau = K_p(q_{\mathrm{target}}-q)-K_d\dot q
$$

部署发送的期望速度和前馈力矩均为 0，关节目标与训练对应的 kp、kd 一起交给低层控制。

代码位置：[src/supermimic/policy/nets.py](../src/supermimic/policy/nets.py) 第 18–29 行和第 51–82 行；[src/supermimic/envs/actions.py](../src/supermimic/envs/actions.py) 第 58–68 行；[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py) 第 211–223 行。

### 4.4 每轮先用物理仿真收集数据

Trainer.run 调用当前策略得到动作，再交给 env.step。仿真端执行时加入默认标准差 0.1 的高斯动作噪声，增加世界模型见到的动作范围。

ReplayRecorder 记录：

~~~text
状态 s
策略干净动作 a
加噪后的执行动作 a_exec
环境上下文 xi
奖励 r、终止标记
当前动作片段及参考帧
~~~

状态 s 为 71 维，包括根部位置、姿态、关节角以及相应速度。默认上下文 xi 为 33 维，包括脚底摩擦、29 个关节标定偏差和躯干质心偏移，提供给世界模型和 critic。

观测中的 previous action 保留干净的策略输出；世界模型拟合使用 a_exec。这样可以同时保持策略输入约定和动力学监督的一致性。

代码位置：[src/supermimic/training/loop.py](../src/supermimic/training/loop.py) 第 284–301 行；[src/supermimic/data/recorder.py](../src/supermimic/data/recorder.py) 第 68–119 行；[src/supermimic/envs/actions.py](../src/supermimic/envs/actions.py) 第 1–13 行及第 58–87 行；[src/supermimic/envs/sim_context.py](../src/supermimic/envs/sim_context.py)。

### 4.5 世界模型学习“动作怎样影响下一步状态”

世界模型可以写成：

$$
\hat s_{t+1}=f_\omega(s_t,a_t,\xi)
$$

实际实现由多个部分组成：

| 部分 | 实现方式 | 原因 |
|---|---|---|
| 动力学 | 神经网络学习 | 接触、执行器和状态演化需要从交互数据拟合 |

### 4.6 冻结世界模型，在预测轨迹中优化策略

更新策略时，从回放缓存中抽取状态和观测历史作为起点，在世界模型里连续展开默认 32 步，约 0.64 秒：

~~~text
观测与目标 → 策略动作 → 世界模型预测下一状态
                           ↓
                    计算奖励与终止概率
                           ↓
                   生成下一步观测与目标
                           ↓
                         重复
~~~

策略目标为：

$$
J(\theta)=\mathbb E\left[
\sum_{t=0}^{H-1}\gamma^t c_t\hat r_{t+1}
+\gamma^Hc_HV_\psi(\hat s_H,g_H,\xi)
\right]
$$

其中：

- H 默认是 32。
- c 是软存活权重，按 c[t+1] = c[t] × (1 − predicted_done[t+1]) 累积。
- 前半部分衡量展开窗口里的动作表现。
- 末尾的价值网络估计窗口之后的收益，减轻短视问题。

更新时冻结世界模型和 critic 的参数，但保留它们对输入的梯度。因此奖励变化可以沿“状态—动作—策略”整条预测链传播到策略参数。然后再用这批预测轨迹的 GAE 目标拟合 critic。

critic 能看到完整仿真状态、环境参数，以及额外的根部位置/偏航误差；策略仍然只使用前面定义的可部署观测。部署不需要把 critic 的特权输入补齐。

代码位置：[src/supermimic/imagination/policy_trainer.py](../src/supermimic/imagination/policy_trainer.py) 第 65–140 行；[src/supermimic/imagination/rollout.py](../src/supermimic/imagination/rollout.py) 第 37–165 行；[src/supermimic/imagination/objective.py](../src/supermimic/imagination/objective.py) 第 10–35 行；[src/supermimic/policy/nets.py](../src/supermimic/policy/nets.py) 第 85–96 行。

**物理仿真采样、世界模型更新和策略更新是交替进行的。** 新策略产生新状态分布，后续仿真数据继续改进世界模型，所以不能把它理解成“先离线训练一个固定世界模型，然后一直只在里面训练策略”。

### 4.8 难动作如何得到更多训练机会

默认把动作时间轴切成 1 秒的小区间，记录从每个区间开始的回报。重置起点由三部分混合：

- 50%：在区间上均匀抽样。
- 40%：偏向回报低、当前策略还不擅长的区间。
- 10%：按照历史难例权重抽样。

这样既保持动作覆盖，也集中训练困难片段。当前实现还对剩余时间归一化回报，避免动作末尾仅因剩余时间短、累计奖励低而被误判为难例。

实机微调另有两种可选机制：

| 机制 | 改变什么 | 作用 |
|---|---|---|
| fail-reset | 从已知失败帧之前的时间窗口取参考起点 | 更多训练发生在困难动作附近 |
| real-reset | 用实机日志重建出的机器人状态作为起点 | 覆盖实机真正到达过的偏离状态 |

两者含义不同，也不应简单将配置中的概率相加。代码在常规参考重置流程中进一步选择部分环境应用实机状态。

代码位置：[src/supermimic/envs/mdp/commands.py](../src/supermimic/envs/mdp/commands.py)，hard_distribution（第 487 行）、_apply_fail_resets（第 506 行）、_sample_frames_mixture（第 521 行）、sample_real_states（第 545 行）、_resample_command（第 587 行）；[METHOD.md](METHOD.md) 第 117–129 行。

### 5.3 e24 最后一轮新增的三类处理

在上述基础上，最后一轮增加：

1. **实机状态重置**：使用三次失败运行提取的 87 个状态，20% 的重置从这些状态开始，根部线速度采用参考动作的值。
2. **局部推力随机化**：在两次转体/起跳之间的指定时间窗口，以 0.2 的 episode 概率施加短时骨盆力或力矩扰动。
3. **腰部 roll 模型调整**：范围改为 ±0.72 rad，并随机化额外阻尼和摩擦。

仓库没有对这三项做独立消融，因而只能确认“这组设置得到一个成功模型”，不能确认其中某一项独立导致成功。

### 5.4 实机日志怎样变成可用于训练的初始状态

build_real_reset_states.py 逐行读取选定的实机日志：

| 状态量 | 来源/重建方式 |
|---|---|
| 关节 q、dq | 直接取实机测量 |
| 骨盆姿态 | 取实机 IMU 四元数，航向重新对齐到参考动作 |
| 骨盆角速度 | 取实机陀螺仪 |
| 根部 xy | 采用对应参考帧的位置 |
| 根部高度 | 依据 FK 和脚底碰撞几何，把最低接触点放到地面附近 |
| 根部线速度 | 保存参考速度和支撑脚零速度估计两个版本，训练时选择 |

所以，这些起点是“实机测量 + 参考数据 + 接触假设”重建出的状态，并非直接测得的完整机器人真值。

训练端再对高度、倾斜、关节角及速度加入小幅扰动，将这些状态写回仿真，并把参考动作进度同步到相应帧。后续仍使用同一套“仿真采样—世界模型—策略优化”流程。

这个设计的价值在于：训练能够遇到真实失败前的状态分布。例如真实机器人已经侧倾、膝关节已经塌下去时，策略仍有机会学习怎样继续完成动作或恢复姿态。

还要注意帧对齐：实机日志 frame=f 的传感器状态对应参考 f−1，脚本将其存为 ref_frame=f−1。这个差一帧的关系影响“状态和接下来目标”能否正确对应。

## 7. 上实机前，Sim2Sim 实际验证了什么

### 7.1 共用 DeployCore，让测试覆盖真正的部署行为

仿真测试和真机 runner 共用同一个 DeployCore，观测构造、历史堆叠、目标帧读取、ONNX 推理、动作变换和核心中止检查都走同一实现。

这一点比单纯“在仿真里播放 PyTorch 模型”更接近部署：可以提前发现网络之外的接口错误，例如历史顺序、时间错位、动作缩放和限幅行为。

当前训练和这套 Sim2Sim 同属 MuJoCo 生态：训练使用 GPU 并行的 MuJoCo Warp，部署测试使用 CPU MuJoCo，并进一步换成 Unitree 的机器人模型。其迁移差异包括计算路径、模型参数、执行器实现和通信延迟。

代码位置：[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py) 第 1–11 行；[docs/SIM2SIM.md](SIM2SIM.md) 第 24–40 行。

### 7.3 实机特性必须进入测试模型，测试结果才更有解释力

e24 的模型筛选启用了：

- IMU 角速度饱和及由此产生的姿态误差模型。
- 腰部 roll/pitch 耦合。
- 腰部 roll 的范围和阻尼修正。
- 延迟、kp、质量、摩擦组合测试。

在 ground profile 下，G2 共 36 组：3 个延迟值 × 6 组 kp/质量组合 × 2 个摩擦系数。

作者记录的比较是：

| checkpoint | 启用上述真机模型的 ground G2 |
|---|---|
| e24_0355000 | 0 次中止、0 次跌倒，最差倾斜误差约 13.0° |
| 父模型 lean35kfs 342k | 4 次中止、3 次跌倒，最差倾斜误差约 24.7° |

文档同时指出，不加入这些真机模型时，不少失败 checkpoint 也能得到 0/36 中止。因此测试场景是否包含真实失败机制，比单看一个 PASS 更重要。

还有一个必须保留的限制：**e24 在包含更严格 slack profile 的正式 --clips 总体规则下仍为 FAIL，成功实机运行采用的是 ground profile。** real-state gate 的跌倒数、clean rate 和某些 1 kHz 膝速度指标也没有可靠预测实机结果。作者最终采用的筛选规则是基于少量模型事后总结的经验，尚未证明适用于新动作。

### 8.1 Python 负责策略，C++ 负责 DDS 通信

### 8.2 每个策略周期实际做的事情

以 50 Hz 为例，每 20 ms：

1. 读取最新关节角、关节速度、骨盆 gyro 和 IMU 四元数。
2. 生成 93 维本体观测，更新 930 维历史。
3. 从参考表取接下来的 10 帧，组成 680 维目标。
4. ONNX 推理得到 29 维动作。
5. 计算 q_target = q0 + scale × action。
6. 做非有限值、倾斜、速度和动作幅度检查，按配置约束目标对应的 PD 力矩。
7. 交给 bridge 持续发布带目标、kp、kd 的低层指令。

因此，参考动作时间按周期推进，而控制输出会随测到的机器人状态变化。它能够产生与参考关节角不同的目标来保持平衡、吸收落地冲击。

代码位置：[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py)，step（第 191–209 行）、targets（第 211–223 行）、_check（第 225–244 行）；[docs/DEPLOY_G1.md](DEPLOY_G1.md) 第 154–165 行。

### 8.3 启动和结束依靠状态机管理

主要状态流转：

~~~text
PASSIVE
  → INTERP：平滑接近动作首帧
  → HOLD：以站姿增益保持
  → STANDBY_PRE：策略接管，在静态参考上维持平衡
  → POLICY：参考帧开始推进，执行动作
  → STANDBY_POST：策略继续在末帧静态参考上维持平衡

异常或遥控器 L2+B
  → DAMP：低刚度阻尼状态
~~~

R1+A 从 HOLD 进入 STANDBY_PRE；R1+X 再开始动作。待机到动作、动作到末帧待机时，通过 switch_clip 更换参考，保留观测历史和上一动作，减少输入突然重置。

待机通过 static_clip 将参考速度归零，策略仍然工作。它依靠闭环策略平衡，与只固定一个关节姿态并使用固定 PD 保持有不同含义。

代码位置：[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py)，switch_clip（第 185–189 行）、static_clip（第 252–259 行）；[scripts/deploy/bridge/g1_runner_bridge.py](../scripts/deploy/bridge/g1_runner_bridge.py) 第 1037–1150 行；操作定义见 [docs/DEPLOY_G1.md](DEPLOY_G1.md) 第 192–220 行。

### 8.4 保护逻辑分布在推理核心、runner 和 bridge 三层

| 层级 | 典型检查/行为 |
|---|---|
| DeployCore | 倾斜相对参考超过约 20°、关节超速、动作异常、NaN/Inf、IMU 四元数异常 |
| Python runner | 状态包过期、策略循环超时、温度、电机错误、控制模式变化、遥控器、其他发布者 |
| C++ bridge | runner 超过约 100 ms 未更新指令、进程消失或 bridge 收到 SIGTERM 时，独立锁定阻尼输出 |

bridge 默认在 runner 消失后继续发送阻尼约 10 秒。这样 Python 崩溃时，不必依赖 Python 自己执行清理逻辑。

部署阶段 air、feet、slack、ground 使用不同速度、动作幅度和力矩约束；POLICY/策略待机时相对参考的倾斜阈值仍约 20°。ground 表示该阶段的配置，不意味着已经验证无保护绳运行。

代码位置：[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py) 第 104–115 行和第 225–244 行；[scripts/deploy/bridge/g1_runner_bridge.py](../scripts/deploy/bridge/g1_runner_bridge.py) 第 148–157 行、第 629–709 行；[scripts/deploy/bridge/g1_bridge.cpp](../scripts/deploy/bridge/g1_bridge.cpp) 第 384–400 行；[docs/DEPLOY_G1.md](DEPLOY_G1.md) 第 331–342 行、第 437–456 行。

### 8.5 温度处理和限幅都来自具体实机问题

长舞蹈中电机温度会上升。仓库增加了启动前温升预测和动作中的平滑热停止：

- 利用策略待机阶段的一段温度历史，估计执行完整动作后的温度。
- 达到热停止条件时，把参考平滑过渡为静态参考，让策略继续平衡。
- 更严重的过热等异常仍进入 DAMP。

这源于作者记录的“动作中直接进入 DAMP 后跌倒”。DAMP 是阻尼状态，不保证机器人能够站住。温度默认阈值属于项目工程配置，原文对硬件额定适配仍标有未验证；不能把实机示例中提高过的阈值当成厂商认可的通用值。

限幅也有一个容易误解的点：DeployCore 默认不裁剪关节目标到软角度范围，而是开启基于 PD 力矩的目标约束。原因是训练没有这种目标裁剪，作者测试中额外裁剪会改变控制行为并恶化跟踪。关节目标可以超过角度范围以形成所需 PD 力矩，但实际关节仍受物理限制；这并不意味着碰到机械限位没有风险。

代码位置：[scripts/deploy/bridge/g1_runner_bridge.py](../scripts/deploy/bridge/g1_runner_bridge.py)，thermal_stop_clip（第 1521 行）、温升预测逻辑（第 1255 行附近）；[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py) 第 104–112 行和第 211–223 行；[docs/DEPLOY_G1.md](DEPLOY_G1.md) 第 168–173 行、第 479–504 行。

## 9. 这套方案怎样利用实机失败改进下一版

转体落地舞蹈展示了完整的迭代链：

~~~text
实机失败日志
    → 定位失败时段和异常状态
    → 判断涉及参考动作、传感器、执行器还是策略行为
    → 修改参考动作、仿真/观测模型或训练分布
    → 继续训练世界模型和策略
    → 导出各 checkpoint，并重新做部署侧测试
    → 选择候选模型再验证
~~~

仓库记录的三个代表性问题如下：

| 观察到的问题 | 为什么原有仿真可能没暴露 | 仓库的处理 |
|---|---|---|
| 转体时骨盆 gyro 饱和，随后重力方向观测出现误差 | 仿真观测接近理想状态 | 修改参考转速，训练和测试加入 IMU 饱和模型，增加角速度惩罚 |
| 腰部目标在实机无法达到，身体继续倾斜 | MJCF 将腰 roll/pitch 近似为独立关节，范围和阻尼也不完全匹配 | 根据日志加入耦合约束，调整 roll 范围和阻尼/摩擦 |
| 单脚落地后突然收腿，膝速度过限 | 策略遇到真实落地状态后产生不合适的反馈动作 | 修改落地参考，增加关节速度惩罚，从失败实机状态重置并加入局部扰动 |

腰部耦合的具体近似为：

$$
|\mathrm{roll}|+1.4|\mathrm{pitch}|\leq0.95
$$

这组系数来自作者实机日志拟合。代码将其作为仿真约束，世界模型再从受约束仿真的状态转移中学习其影响。它不是所有 G1 配置都无需核对的机械定律。

成功模型的落地表现也说明目标跟踪并非逐关节照抄：作者记录它在触地前采用了与参考不同的膝、踝和髋动作，触地后由髋膝共同吸收冲击。在所分析的落地窗口，右膝最大速度约 7.6 rad/s；此前失败模型会在触地后突然收腿并超过速度阈值。

这些数字和机制解释来自作者的日志分析。尤其“哪项训练修改造成改变”的因果关系，仍需要消融才能确认。

## 10. 和普通部署仓库有什么不同，优势在哪里

这里的“普通部署仓库”特指主要完成“读取已有策略—组装观测—推理—SDK 发送命令”的工程，不指所有其他项目。成熟部署工程同样可能具备测试、状态机和 watchdog，以下比较的是本仓库覆盖的工作范围。

| 比较维度 | 以加载策略为主的部署工程 | 本仓库 |
|---|---|---|
| 起点 | 通常已有训练好的模型 | 可以从重定向动作开始 |
| 训练方法 | 训练可能在外部完成 | 自带世界模型和可微策略优化 |
| 动作数据处理 | 读取已准备好的指令/目标 | 重采样、FK、过滤、速度修改、过渡拼接、紧凑库 |
| 训练到部署的一致性 | 依赖配置同步和人工核对 | 常量导出交叉检查、ONNX 数值检查、完整输入输出 parity 测试 |
| 仿真验证对象 | 常见为一次策略回放 | 共用实际推理核心，还测模型扰动、接管、待机与 DDS 故障 |
| 真机不匹配处理 | 可能主要调整部署增益、限幅和通信 | 同时修改参考、仿真模型、传感器模型、奖励与训练起点 |
| 实机日志用途 | 状态排查和结果展示 | 还可重建训练起点，进行针对性微调 |
| 实机计算 | 策略推理 | 同样只需策略推理，世界模型不会增加机载在线规划负担 |

### 10.1 优势一：训练梯度能利用动作对未来状态的影响

可微世界模型让“改变一个动作，会怎样影响后续姿态、接触表现和奖励”形成可求导的近似链条。配合短时展开和 critic，可以在学习到的动力学内优化控制行为。

这是算法层面的优势来源，但实际效果取决于世界模型的准确度和训练状态覆盖；错误的模型也可能提供错误梯度。因此仍需要物理仿真持续校正数据分布，不能据此断言它在所有任务上都比 PPO 更快、更稳定。

依据：[src/supermimic/imagination/policy_trainer.py](../src/supermimic/imagination/policy_trainer.py) 第 70–93 行；[src/supermimic/imagination/objective.py](../src/supermimic/imagination/objective.py) 第 10–20 行。

### 10.2 优势二：同一个目标条件策略可以覆盖多段动作

策略通过目标窗口接收动作意图，动作库和共享世界模型允许多个片段一起训练。编码器提取短期运动信息，解码器结合当前机器人状态输出动作，有利于复用已有运动控制能力。

紧凑动作库、向量化仿真和多卡梯度同步为大规模训练提供了工程基础。仓库报告 e11c 在约 12.95 万段 BONES-SEED 动作上评测；这属于作者的仿真结果，不能转换成同等数量动作的真机成功承诺。

依据：[src/supermimic/policy/nets.py](../src/supermimic/policy/nets.py) 第 51–82 行；[src/supermimic/envs/mdp/motion_library.py](../src/supermimic/envs/mdp/motion_library.py) 第 1–24 行；[src/supermimic/training/distributed.py](../src/supermimic/training/distributed.py)；结果见 [METHOD.md](METHOD.md) 第 7–22 行。

### 10.3 优势三：把可上机的观测接口贯彻到训练

策略只要求关节状态、IMU 和上一步动作，不依赖当前全局位置或基座线速度。这减少了额外定位系统和状态估计接口的需求。训练可使用完整状态计算奖励和价值，但部署策略输入保持受限。

这种好处伴随能力边界：没有全局位置反馈时，不应假定它能长期消除位置和航向漂移。参考轨迹的路径与实机实际路径仍可能不同。

依据：[METHOD.md](METHOD.md) 第 35–44 行；[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py) 第 162–181 行。

### 10.4 优势四：部署故障能转化成下一轮训练任务

实机日志不仅用于“看哪里摔了”。仓库将其用于拟合机械约束、模拟观测失真、修改参考动作、选取失败前时间窗口，以及构造实际偏离状态的训练起点。

因此面对“仿真能跑、实机某一帧总失败”，能够逐层排查和修正。比起仅在推理端改几个参数，这种反馈路径覆盖了导致失败的更多来源。

依据：[scripts/data/build_real_reset_states.py](../scripts/data/build_real_reset_states.py)、[scripts/train/train_lean35kfs_e24.sh](../scripts/train/train_lean35kfs_e24.sh)、[docs/REAL_ROBOT_LEAN35KFS.md](REAL_ROBOT_LEAN35KFS.md)。

### 10.5 优势五：工程测试覆盖到了接管、等待和结束

真实部署往往会在“开始动作之前”和“动作结束之后”出问题。策略待机、历史连续切换、温升预测、独立通信桥和端到端故障测试，把这些阶段也纳入设计。

这些机制的价值是减少已知接口和运行故障、帮助定位问题；它们并不等同于对任何动作和任何机器人都成立的稳定性保证。

依据：[docs/DEPLOY_G1.md](DEPLOY_G1.md) 第 192–220 行、第 479–504 行、第 635 行以后的端到端测试说明。

## 11. 理解效果时，应保留哪些边界

### 11.1 已验证范围较具体

作者记录了约 46 秒四段组合舞蹈的一次完整执行，以及 e24 转体落地舞蹈的两次连续完整执行。e24 对应约 21.9 秒、1097 帧的特定动作，使用同一个 checkpoint，保护绳仍连接但放松。

### 11.2 发布模型与复现起点并不齐全

e24 的直接父 checkpoint 没有发布，源动作的部分中间处理、早期失败日志也未全部公开。仓库提供了最终模型、处理后的动作及重置状态等发布产物，但无法仅凭训练脚本从公开父模型逐位重现原始 e24。

训练脚本可以作为配方参考，也可以继续微调已发布 e24；它不能被当成完整、无缺口的从零训练记录。

记录位置：[scripts/train/train_lean35kfs_e24.sh](../scripts/train/train_lean35kfs_e24.sh) 第 8–23 行；[docs/REAL_ROBOT_LEAN35KFS.md](REAL_ROBOT_LEAN35KFS.md) 第 42–54 行。

### 11.3 论文功能、默认设置与实机新增功能需要分开看

仓库没有实现论文的全部接口和实验，例如速度命令接口及其蒸馏/RL 编码器、相关 PPO 对照和若干消融。当前重点是运动参考跟踪。

部分早期文档以基础配方为上下文，例如写“没有 push”或“延迟/PD 随机化不在训练中”；后续 e24 已通过显式参数加入这些功能。解读时应优先看目标模型的实际训练命令、保存的 config 和对应源码，避免把默认配置描述套到后期实机模型上。

记录位置：[METHOD.md](METHOD.md) 第 66–75 行、第 197–230 行；[scripts/train/train_lean35kfs_e24.sh](../scripts/train/train_lean35kfs_e24.sh) 第 55–78 行。

### 11.4 动作参考和仿真模型仍是性能上限的重要来源

若动作要求超过执行器能力、IMU 范围或可达支撑姿态，继续训练未必能解决；需要修改动作参考或模型。e24 的成功过程本身包含多轮参考修改。

同理，将该方案迁移到另一种机器人，需要重新处理机器人模型、FK、关节与观测维度、增益和动作缩放、身体跟踪集合及通信接口。这里多个模块明确使用 G1 的 29 维接口，仅替换 SDK 发布部分不足以完成迁移。

代码位置：[src/supermimic/data/motion_convert.py](../src/supermimic/data/motion_convert.py) 第 35–81 行；[src/supermimic/policy/nets.py](../src/supermimic/policy/nets.py) 第 13–15 行；[src/supermimic/deploy/core.py](../src/supermimic/deploy/core.py) 第 22–26 行；[src/supermimic/envs/tracking_env_cfg.py](../src/supermimic/envs/tracking_env_cfg.py) 第 53–70 行。

## 12. 如果从自己的运动数据继续，应该沿哪条路径做

以下命令用于说明数据和脚本的衔接；需要事先按原仓库文档准备训练环境、机器人模型和数据。本文没有执行这些训练或部署命令。

### 12.1 从已有 G1 CSV 开始

~~~bash
# 从仓库根目录执行；input-fps 应等于实际 CSV 采样率
uv run python scripts/data/csv_to_npz_batch.py \
  --input-dir data/raw/my_motion \
  --output-dir data/npz/my_motion \
  --input-fps 30

# 动作很多或希望固定一个训练数据包时，再打包
uv run python scripts/data/build_library.py \
  --npz-dir data/npz/my_motion \
  --out data/library/my_motion.pt
~~~

在进入训练前，应先检查动作坐标和关节顺序，查看关节速度与转体速度，处理起止站姿及过渡。对应工具见本文第 3 节。

### 12.2 先明确是基础训练还是继续微调

从头训练的基本入口：

~~~bash
uv run sm-train \
  --run-name my_motion_base \
  --data.npz-dir data/npz/my_motion \
  --env.num-envs 4096 \
  --policy-trainer.batch-size 4096
~~~

这只表示“用这些数据运行默认训练”，不表示已经得到实机成功模型。

继续训练时，需选择与目标观测接口匹配的 checkpoint。以下仅以从 220000 步继续到 234000 步为例：

~~~bash
# 必须替换为自己实际存在、接口匹配的训练 checkpoint
PARENT_CKPT=/absolute/path/to/ckpt_0220000.pt

uv run sm-train \
  --run-name my_motion_ft \
  --resume "$PARENT_CKPT" \
  --resume-reset-sampler \
  --data.library data/library/my_motion.pt \
  --env.num-envs 4096 \
  --policy-trainer.batch-size 4096 \
  --schedule.total-iterations 234000 \
  --schedule.lr-constant 1e-5
~~~

这里 total-iterations 是恢复后的累计终点，不是额外增加的步数。对于具体实机问题，再选择相应的倾斜/速度奖励、延迟和机械随机化、失败窗口或实机状态重置；不要把 e24 的特定动作帧窗口直接套到其他动作。

代码位置：[src/supermimic/config.py](../src/supermimic/config.py) 第 168–202 行；完整实机配方见 [scripts/train/train_lean35kfs_e24.sh](../scripts/train/train_lean35kfs_e24.sh)。

### 12.3 导出后验证，验证后才进入实机流程

需要依次形成：

~~~text
训练 checkpoint
    → deploy_config.json
    → policy.onnx
    → 部署目标表 clips/动作.npz
    → G1/G2/G3/standby 等相应测试
    → DDS 端到端测试
    → 实机只读检查、接管与逐阶段运行
~~~

导出脚本有现成数据依赖，当前版本不能把所有步骤都当成完全通用的“任意 checkpoint 一键导出”：

- config、onnx、mjcf 路径需要文档指定的 BONES-SEED neutral_idle_loop_001__A081.npz。
- ONNX 的真实形态输入一致性检查还需要至少一个内置测试动作的已导出目标表。
- --npz-dir 参数主要控制 clips 导出的源目录，不会自动替换所有其他步骤的数据依赖。
- 若使用发布模型，要显式指定模型名称。部分脚本默认值仍指向未公开的旧模型。
- PC2 的 ONNX Runtime 兼容性要按发布包说明处理：早期包需要选择 IR9 版本，e24 发布包的 policy.onnx 已是 IR9。

因此，应直接按 [docs/SIM2SIM.md](SIM2SIM.md) 第 5–22 行的导出顺序准备产物，再按 [docs/DEPLOY_G1.md](DEPLOY_G1.md) 执行对应机器上的流程。

已经准备好 e24 发布产物时，以下是其专用的仿真筛选入口：

~~~bash
bash scripts/train/gate_lean35kfs.sh e24_0355000
~~~

该脚本读取 G1_DEPLOY_HOME 指向的部署环境，并依赖对应动作和模型文件；其缓存的已有结果可能被复用，比较新参数或新产物时要核对输出来源。实机入口为 [scripts/deploy/bridge/g1_runner_bridge.py](../scripts/deploy/bridge/g1_runner_bridge.py)，具体参数和按钮顺序以 [docs/DEPLOY_G1.md](DEPLOY_G1.md) 为准。
